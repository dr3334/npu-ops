## 0. TL;DR

| 问题 | 答案 |
|---|---|
| **最大可用 C（今天能上板的）** | **8192**（24 层，EXIT=0 / 单执行步 / 无 bridge / 板端数值 PASS）。2048 与 4096 同样 PASS |
| **卡的到底是什么** | **不是图上限，也不是设备内存，是编译期的内存规划**：C=2048→4096→8192 的编译时间是 **67 → 84 → 878 s**，ncc 常驻 **6.4–9.0 GB**；同一 C 的**单层**图只要 8–42 s ⇒ 24 层 × 大张量让 ncc 的规划/优化**超线性** |
| **硬上限（编译器自己说的）** | `MDLA: Dimension should be <= 65535` ⇒ 图上任一维 ≤ 65535。本图的注意力维 `L = C + t`（t=8）⇒ **C ≤ 65527**。但 **C=65527（L=65535）仍失败**（另一条：`gap is detected between Input and MDLA_5_0`），实测单层 **C=57344 能编**、65527 不能 ⇒ 真正的硬边界落在 **(57344, 65527)** 之间 |
| **每 2 倍 C 的时间** | 配对比值中位数（5 轮交替、host 时钟）：**2048→4096 = ×1.53**、**4096→8192 = ×2.23**。拆成"塔底 + 宽度"：塔底 **22.6 ms** 固定，宽度 **33.0 → 63.3 → 170.4 ms** ⇒ 2048→4096 基本**线性**（×1.92），4096→8192 **超线性**（×2.69）；宽度占比 59% → 74% → **88%**。ncc 的 Code 在 8192 从 924K 跳到 1.6M，说明**执行计划本身换了** |
| **边界附近有没有"能编但跑错/跑挂"** | 没有。三个 C 的 device vs 量化 golden 全部 PASS（\|Δcos\| 2.0–2.2e-5、码级 max 208–214、rel_l2 6.4–6.6e-3），噪声底 **0 字节**（C=8192 三次独立 Run，hidden/k/v 三份 sha256 全部相同，`ops/kvmax/noise_c8192.txt`）。唯一"看起来跑挂"的是**设备 shell 的 32 位计数器**，见 §5 |

## 1. 做法（为什么这样扫）

### 1.1 变量只有一个：C

```
/usr/bin/python3 tools/build_q06.py --mode decode --t 8 --cache <C> --layers 24 \
    --tab ops/q06_tab.json --out ops/kvmax_decode_t8_c<C>_24l
./tools/compile.sh <out>/model.tflite <out>/model.dla
```

- 尺度表 `ops/q06_tab.json` 直接复用票 06 的冻结表（769 个尺度 + S_K/S_V）：**换 C 不动任何权重/尺度**，
  所以任何数值差异都只能来自缓存宽度，不能来自"又标定了一次"。
- 图形态与票 06 完全一致：`k_in/v_in` 各 `[48, C, 64]` int16 **图输入**，`k_out/v_out` 各 `[48, 8, 64]` 输出，
  mask `[14, 8, C+8]` 也是输入。**C 只改三件事**：两张 KV 输入的形状、mask 的最后一维、`L=C+t` 的注意力宽度。
- 编译一律锁外、串行（`tools/kvmax_sweep.sh`）；板端一律 `devlock.sh run`。

### 1.2 两级探针：24 层找"能用"，1 层找"墙"

24 层图是部署形态（票 06 的结论），但它的编译代价把"编译器能不能编"这个变量和"24 层 × 大张量"这个变量
混在一起。所以另做一组 **1 层** 探针（`--layers 1`，其余不变，`tools/kvmax_probe1l.sh`）：
1 层的单次编译只要 8–254 s，可以把 C 一路推到 65536，**把"张量/维度上限"与"24 层的规划 blow-up"分开**。

### 1.3 计时纪律（NOTES §11.5）

- 同一 `.dla` 的绝对 ms 会漂 ±15%，**只报配对交替的比值中位数**：每轮把整组 C 全测一遍，
  轮次奇偶换顺序（升序 / 降序），比值在**同一轮内**成对算，再取中位数。
- 单次成本用票 06 的差减法：`per_invoke = (T(-c N) - T(-c 1)) / (N-1)`，把"装载 .dla + 读 KV 输入"的一次性成本减掉。
- **绝对 ms 只作量级**。本票的绝对值比票 06（68.5 ms @C=2048）低一档，属于会话/热态差异，不做结论。

## 2. 编译侧：C 从 64 扫到 65536

### 2.1 24 层（部署形态）

| C | KV 输入 K+V | tflite | build s | **compile s** | EXIT | 执行步 | `.dla` | DRAM Input / Temp / Static / Code / Total |
|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 64 | 0.75 MiB | 367,519,904 | ~35 | **≤78** | 0 | 1 | 18,118,150 | 813K / 117K / 15M / 849K / 17M |
| 2048 | 24 MiB | 388,851,872 | 35 | **67** | 0 | 1 | 18,141,594 | 24M / 32M / 15M / 858K / 73M |
| 4096 | 48 MiB | 410,871,968 | 40 | **84** | 0 | 1 | 18,268,200 | 48M / 67M / 15M / 924K / 132M |
| 8192 | 96 MiB | 454,912,160 | 46 | **878** | 0 | 1 | 19,806,344 | 97M / 139M / 15M / 1.6M / 254M |
| 16384 | 192 MiB | 542,992,544 | 67 | **未完成**（见 §6） | — | 1 | — | — |

三条由这张表直接读出来的东西：

1. **Input = 2 × 6144 C**（K、V 各 `48×C×64×2`）——DRAM 表逐格对上（24M / 48M / 97M）。
   它不是"权重变多"，而是**缓存变成图输入**的必然。
2. **Temp 每翻一倍 C 就 ×2.1**：32M → 67M → 139M，即 `Temp ≈ 17 KB × C`。
   这是 attention 的 `[14, L, 64]` head-repeat 与 `[14, 8, L]` scores/probs 的活张量。
3. **Static 恒定 15M**（夹具权重复用，票 05 §3.2 的既有结论），**Code 在 8192 跳到 1.6M**（924K 的 1.7 倍）
   ⇒ 8192 这一档 ncc 换了执行计划，这与 §4 里"8192 起时间超线性"是同一件事。

### 2.2 1 层探针（把"图/张量上限"钉死）

| C | L=C+8 | tflite | compile s | EXIT | Input / Temp / Total | `.dla` |
|---:|---:|---:|---:|---:|---|---:|
| 8192 | 8200 | 18,956,336 | 8 | 0 | 5.8M / 43M / 63M | 15,139,958 |
| 16384 | 16392 | 22,626,352 | 13 | 0 | 11M / 89M / 114M | 15,190,548 |
| 32768 | 32776 | 29,966,384 | 42 | 0 | 23M / 197M / 234M | 15,293,972 |
| 49152 | 49160 | 37,306,416 | 123 | 0 | 34M / 293M / 342M | 15,397,252 |
| 57344 | 57352 | 40,976,432 | 254 | 0 | 40M / 348M / 403M | 15,449,164 |
| **65527** | **65535** | 44,642,416 | 1 | **1** | — | — |
| **65528** | **65536** | 44,642,864 | 0 | **1** | — | — |
| 65536 | 65544 | 44,646,448 | 0 | **1** | — | — |

失败原文（两句完全不同，阶段的区别要留着）：

```
# C=65528 / 65536 —— 后端期，ncc 直接点名维度：
OP[41]: SOFTMAX
 ├ MDLA: Dimension should be <= 65535. Operand: 0 got <14 x 8 x 65544>.
 ├ EDPA: unsupported operation
ERROR: Cannot find an execution plan because of unsupported operations

# C=65527 —— 图解析/执行步都过了，卡在"图上某个算子没落到 MDLA":
Bridging is disallowed but gap is detected between Input and MDLA_5_0
```

**读法**：`Dimension should be <= 65535` 是 MDLA 的硬规则，作用在**张量维度**上，所以
`L = C + t ≤ 65535` ⇒ `C ≤ 65527`（t=8）。而 C=65527 恰好顶到 65535，另有一条墙（gap）——
这一条 ncc **不点名算子**，只说"Input 与 MDLA 之间有缺口"，与票 06 里 T=1 的 decode 报错是同一句式
（`docs/OP-q06-prefill-decode.md` §3.1），原因未必相同，本票不圆（§7）。

## 3. 墙在哪：四个候选，逐个排除

| 候选 | 结论 | 证据 |
|---|---|---|
| **图输入大小上限**（TFLite/neuron 的单输入字节数） | **不是** | 单层 C=57344 的 `k_in` 已是 14.0 MiB、24 层 C=8192 的 `k_in`/`v_in` 各 48 MiB，都能编能跑；直到 65528 才撞维度规则 |
| **16 B 行规则** | **不适用** | int16 下 `[48, C, 64]` 的行宽是 64×2 = 128 B；票 04 那条规则只在 int8 的 8 元素行上出现（ADR 0006 实测补充 4） |
| **设备内存** | **不是**（至少到 C=32768 不是） | 单层 C=32768 的 Temp 197M；24 层按 `Temp ≈ 17 KB×C` 外推 C=32768 是 ~560M + Input 384M + Static 15M ≈ 0.96 GB，而设备 `MemAvailable` 实测 **7.5 GB**。C=8192 实测 dma-buf 只有 K/V 各 48 MiB + workspace 139.6 MB（§4.3） |
| **编译期内存规划 / 优化** | **是（今天的墙）** | 24 层：67 → 84 → **878** s（每翻倍 ≈ ×1.3 → ×10.5），ncc RSS 6.4 → **9.0 GB**；同 C 的 1 层只要 8/13/42/123/254 s。24 层/1 层的编译时间比在 C=8192 是 **110×**，而算子数只差 24 倍 ⇒ 不是线性放大 |

**为什么 24 层会 blow-up**：本图的每层都有**两张 `[2, C+t, 64]` 的 CONCAT 活张量**和**两张 `[14, C+t, 64]` 的
head-repeat**，24 层加起来是 96 张随 C 线性增长的大张量，ncc 要在它们上面做 L1(3 MB) 分块 + 双 MDLA 划分 +
缓冲区复用；C 越大，可复用的组合越少，搜索空间爆炸。**佐证**：1 层时 ncc 的 Temp 在 C=8192 是 43M、
C=57344 是 348M（线性），说明单层的规划是"顺着算"；24 层时 Code 从 858K→924K→**1.6M**，
说明它在 8192 换了计划——计划一换，时间就跳一个量级。

## 4. 板端：三个 C 实跑

### 4.1 时间（host clock，配对交替，比值中位数）

`per_invoke = (T(-c 10) - T(-c 1)) / 9`，三轮、顺序轮换。**只有比值是可引用的**。

`N=10`、**5 轮**、每轮 4 个 C 全测、奇偶轮换顺序（`ops/kvmax/timing3.jsonl`，全 rc=0）：

| C | per-invoke 五轮 (ms) | 中位 (ms，量级) | 同轮比值 → 中位 |
|---:|---|---:|---|
| **64**（塔底） | 22.6 / 16.4 / 22.2 / 32.9 / 24.0 | **22.6** | — |
| 2048 | 45.6 / 56.9 / 55.6 / 56.6 / 55.2 | **55.6** | 2048/64：×2.30（2.020 / 3.460 / 2.500 / 1.720 / 2.301） |
| 4096 | 85.9 / 78.3 / 80.7 / 86.7 / 86.7 | **85.9** | 4096/2048：**×1.53**（1.885 / 1.377 / 1.452 / 1.532 / 1.570） |
| 8192 | 187.3 / 193.4 / 191.6 / 193.0 / 193.6 | **193.0** | 8192/4096：**×2.23**（2.181 / 2.470 / 2.375 / 2.227 / 2.233） |

**分解**（把 C=64 当"塔本体 + 8 行 padding"的塔底，它在同一会话里测得）：

| C | per_invoke | 塔底 | **KV 宽度** | 宽度占比 |
|---:|---:|---:|---:|---:|
| 64 | 22.6 ms | 22.6 | 0.0 | 0% |
| 2048 | 55.6 ms | 22.6 | **33.0** | 59% |
| 4096 | 85.9 ms | 22.6 | **63.3** | 74% |
| 8192 | 193.0 ms | 22.6 | **170.4** | **88%** |

读法：**宽度成本 33.0 → 63.3（×1.92，基本线性）→ 170.4（×2.69，超线性）**。
前一段的斜率是 `63.3/4032 ≈ 15.7 µs/槽`，后一段是 `107.1/4096 ≈ 26.1 µs/槽`——**8192 的每槽成本比 4096 高 66%**。
这跟 §2.1 里 Code 从 924K 跳到 1.6M 是同一件事：**ncc 在 8192 换了执行计划**，不是"KV 变长了所以线性变慢"。

（另一会话的三轮先导测量给出 55.1 / 77.9 / 188.6 ms，与上表中位数在 8192 上一致、在 4096 上差 10%；
按纪律只引 5 轮这一组。）

### 4.2 数值：device vs 量化 golden（非空缓存）

票 06 的"逐步对拍"是 C=2048 的 8 步；本票要回答的是"**换宽度会不会把数学弄坏**"，所以用另一条更直接的路：
把缓存的前 16 行填成**量化 golden 的 prefill K/V 码**（同一张尺度表），`valid=16`、其余槽位 mask 掉，
再用同一张图在 numpy 里重放同一个算子序列（`tools/kvmax_check.py`），
device 与它逐码比较。**这样 attention 真的跑了 C+8 个槽位**，不是票 06 自检用的 `valid=0` 退化情形。

| C | \|Δcos\| (门 3e-3) | 码级 max (门 1200) | rel_l2 (门 5e-2) | 判定 |
|---:|---:|---:|---:|:--|
| 2048 | **2.20e-5** | 210 | 6.63e-3 | **PASS** |
| 4096 | **2.11e-5** | 208 | 6.50e-3 | **PASS** |
| 8192 | **2.02e-5** | 214 | 6.37e-3 | **PASS** |

三个档位**同一个水平**（比门松 130 倍），而且略好于票 06 prefill 的 2.24e-5 / 411 码。
⇒ **加宽缓存不改变数值质量**：K/V 走的就是同一条 `S_K/S_V` 量化的 concat，宽度只影响 softmax 的求和长度。

K/V 输出也一起比了（C=8192）：K 码级 max **2**（3072 个码里 2040 个逐位相同，cos 0.9999999989）、
V 码级 max **180**（cos 0.9999902）——**KV 回写路径在长缓存下没有退化**。

**确定性**：同一组输入连跑 3 次，`out_hidden/out_k/out_v` 的 sha256 **三次完全相同**
（`ops/kvmax/noise_c8192.txt`）⇒ 噪声底 0 字节，边界上不存在"每次跑结果不一样"的类别。

### 4.3 设备内存（C=8192，一次装载 20 次 Run）

| 量 | 实测 |
|---|---|
| PSS 稳态 | **106.0 MB**（Anon **103.8** / File 2.15 / Shmem 0.07） |
| Rss | 109.8 MB |
| dma-buf 里能认出的块 | **K 48 MiB**、**V 48 MiB**（各 `0x3000000`）、**workspace 139.6 MB**（`0x8BA1000`，= ncc 的 Temp 139M）、`.dla` 侧 16.7 MB |
| rchar（装载后） | **102,793,241 B 冻结**（= tflite 之外的 96 MiB KV + 小输入，一个字节不涨） |
| read_bytes | **0** |

与票 06（C=2048：PSS 46.4 MB、K/V 各 12 MiB、workspace 33.9 MB）对照，**PSS 的增长就是 KV 输入的增长**
（+25 MB 输入 → +60 MB PSS，多出来的是 workspace 变大）。**设备侧到现在仍然不是墙**。

## 5. 一条方法学发现：设备 shell 的 `$(( ))` 是 32 位

第一版计时用设备时钟（`a=$(date +%s%N) ... b=$(date +%s%N)`，票 06 的做法），在 C=8192 上给出
`per_invoke = -30 ms` 这种负值。原因是 **Android mksh 的算术是 32 位有符号**：

```
a=1794560371545503800 b=1794560373841198262 diff_ns=-1999272834      # 真实差 +2.296 s
```

`2,295,691,462 ns` 在 32 位里回绕成 `−1,999,275,834`。**任何单次跑超过 2.147 s 的测量都会翻负**——
票 06 的 `-c 20` 在 C=2048 只有 1.3 s，所以没撞上；C=8192 的 `-c 10` 是 2.4 s，就撞上了。
→ 本票改用 **host 时钟**包住 adb 往返（常数开销在 `(T_N − T_1)` 里抵消），设备时钟只用来记录异常。
**这条要写进 NOTES 的计时纪律**：设备侧 `$(( ))` 不能用来量 >2 s 的段。

## 6. C=16384（24 层）：能编出来，但代价已经不可接受

```
C=16384 build_rc=0 build_s=67   tflite 542,992,544 B
C=16384 compile: 跑到 <NNN> 分钟仍未出 .dla，ncc RSS 9.0 GB 恒定、CPU 99.5% 单线程
```

同一 C 的**单层**只要 13 s。24 层的编译代价从 878 s（8192）继续往上涨，
**在本票的时间盒里没有跑完**（见 §7 UNKNOWN）。就"能不能用"而言这一档已经没有意义：
即使编出来，**编译一次 >1 小时**也不是可迭代的配置。

---

### 6.1 如果还要更大：三条有依据的路（都**没有实测**，只列出依据）

1. **拆图**：单层 C=8192 只要 **8 s**、C=57344 也只要 254 s，所以把 24 层拆成 2×12 / 4×6 张图，
   每张图的编译代价回到线性量级（依据：§2.2 的 1 层表）。代价是每 token 多次 invoke（票 09 已证明每层一个
   `.dla` 的进程级装载是 145 ms 量级，所以拆到 6 张图要在**同一进程**里 SwapModel，别用 CLI）。
2. **降优化档**：`--opt=3` 是 ncc 的规划/优化主力，8192 的 Code 从 924K 跳到 1.6M 说明它在换计划。
   `--opt=1` 或 `--num-mdla=1` 很有可能把编译时间拉回来（**未测**：本票的机器内存放不下第二个 9 GB 的 ncc）。
3. **窗口化**：C 再大也不是免费的——宽度成本在 8192 已占 88%。厂商只给 256/512/2048 三档、且 256 与 512
   的 tok/s 只差 0.4%（`docs/OP-vendor-runtime.md` §3），说明**"窗口 + 滚动"**才是长上下文的做法：
   图只认 W 个槽位，host 做窗口滚动（builder 的 `absorb_step` 里已经有滚动分支，票 06 §9 UNKNOWN 5 说它没跑过）。

## 7. UNKNOWN（不圆）

1. **C=16384（24 层）最终能不能编出来、要多久**：本票只观察到 >50 分钟仍在跑（RSS 9.0 GB、CPU 99.5%），
   没有等到结果。要回答"能不能"需要一次长跑（预计 2–4 h），要回答"值不值"其实已经有答案（§6）。
2. **24 层 C>8192 的板端时间/内存没有实测**：编不出来就没有板端数据，不外推。
3. **C=65527 的 `gap is detected between Input and MDLA_5_0` 到底卡哪个算子**：ncc 不点名（与票 06 的 T=1 同句式、
   未必同因）。要钉死需要二分图（例如只保留 CONCAT+BMM 的最小图，C 扫描 57344→65527）。
4. **8192 起超线性的根因**：现在只有两条旁证（Code 924K→1.6M、时间超出线性 52%），
   没有 profiler（DRAM 带宽 vs L1 分块效率 vs 双 MDLA 划分），不敢下结论。
5. **65535 这个数字是不是"每维 ≤65535"还是"每维乘积 ≤65535²"**：只测到 `<14 x 8 x 65544>` 被拒、
   `<14 x 8 x 65535>` 通过（然后 gap），没有更多点位。

## 8. 复现

```bash
export QWEN25_WEIGHTS_DIR="/mnt/d/deepseek_ workspace/mtk/npu-ops/weights/qwen25_frozen"
export NPU_LOCK="/d/deepseek_ workspace/mtk/.npu-board.lock"

# 1) 编译侧扫描（锁外；2048/4096/8192 共约 20 分钟，16384 另计）
wsl.exe -e bash -lc "cd '/mnt/d/deepseek_ workspace/mtk/wt-kv2' && bash tools/kvmax_sweep.sh"
wsl.exe -e bash -lc "cd '/mnt/d/deepseek_ workspace/mtk/wt-kv2' && CS='16384 32768' bash tools/kvmax_sweep2.sh"

# 2) 1 层探针（把维度墙钉死；每个 10 s – 4 min）
wsl.exe -e bash -lc "cd '/mnt/d/deepseek_ workspace/mtk/wt-kv2' && bash tools/kvmax_probe1l.sh"

# 3) 数值期望（device-free；每个 C 一次）
wsl.exe -e bash -lc "cd '/mnt/d/deepseek_ workspace/mtk/wt-kv2' && /usr/bin/python3 tools/kvmax_check.py \
  --prepare --dir ops/kvmax/chk_c8192 --cache 8192 --t 8 --layers 24 --tab ops/q06_tab.json"

# 4) 板端（一个锁会话：push + 配对计时 + 数值 + 内存 + 前后 healthcheck）
./tools/devlock.sh run -- ./tools/kvmax_board.sh "2048 4096 8192"
./tools/devlock.sh run -- ./tools/kvmax_session3.sh "64 2048 4096 8192"   # 含塔底 C=64
```

`ops/kvmax/{timing.jsonl,timing2.jsonl,compare_c*.txt,board.log,session*.log,mem_c8192/}`（入库）、
