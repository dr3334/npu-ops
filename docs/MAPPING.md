# 映射逻辑（MEM ioctl / IOVA / 重定位）—— 每个算子都写清楚

> 适用：MT6897（Titan 1）、apusys 驱动、`/dev/apusys` magic `'A'=0x41`。
> 证据来源：`probe/iolog2.c` 的 PRE/POST 双打日志 + `probe/mem_map_flow.py` + `probe/asset_report.py`。
> 结论都是实测，不是手册推断；未解释的地方明确标 UNKNOWN。

## 1. 三个 MEM 子命令（nr=33，48 字节结构）

| op | 名字 | 请求字段（偏移） | 返回字段 |
|---|---|---|---|
| 0 | **ALLOC** | `size @20`、`align @24`、`type @40` | `handle @0` |
| 1 | **FREE** | `handle @16` | —（驱动**不支持**，只会打印 `not support memory op(1)`） |
| 2 | **MAP** | `handle @16`、`size @24`、`flags @28` | `iova @8` |

抓包里所有调用的实测值：`type=0`、`flags=2`、`align=0x100`（4 KiB 缓冲）/ `0x10`（大缓冲）、
`size` 与申请值一致。**FREE 一次都没被厂商 runtime 调用**（它只在进程退出时靠 fd 关闭回收）。

## 2. 地址落在哪：**不是一个固定段**

| 缓冲 | 大小 | MAP 返回的 iova | 区段 |
|---|---|---|---|
| 命令缓冲 368/32/16、输入/输出 4096、LUT 4096 | ≤ 4 KiB | `0x254…`–`0x259…` | **低段（0x25xxxxxx）** |
| 512×512 权重（动态 FC） | 256 KiB | **`0xcbbc0000`** | **高段（0xcaxxxxxx–0xcbxxxxxx）** |
| 我们自己 ALLOC 的 256 KiB 缓冲 | 256 KiB | `0xcbb8000` | 同一高段 |
| 1024×1024 权重（1 MB） | 1 MiB | **`0xcba00000`** | 同一高段 |
| 我们自己 ALLOC 的 1 MiB 缓冲 | 1 MiB | `0xcba00000`（**与抓取完全相同**） | 大缓冲像是从**固定池**里分配 |

**结论（重要）**：驱动对**大缓冲**返回的是另一段地址，但**两者都是 DLA 可用的设备地址** ——
厂商的命令流里就写着 `0xcbbc0000`，而我们把 256 KiB 缓冲分配到了 `0xcbb8000` 并成功执行
（`FC512 rc=0，0/512 失配`）。

⇒ **绝不能假设地址范围**（不能写 `if (iova < 0x30000000)` 之类的判断），只能"分配返回什么就用什么，
按值重定位"。这也解释了早期那几个"地址看起来不对劲"的困惑。

**大缓冲实测（自建提交器，全部 0 失配、连跑 3 次一致）**：

| 权重 | 抓取时的 IOVA | 我们分配到的 IOVA | 结果 |
|---|---|---|---|
| 256 KiB（512×512） | `0xcbbc0000` | `0xcbb8000` | `0/512` |
| 1 MiB（1024×1024） | `0xcba00000` | `0xcba00000` | `0/1024` |

⇒ 大缓冲不仅可用，而且**分配地址是稳定的**（1 MiB 那次连地址都一样），像是驱动从固定大页池里给。

**UNKNOWN**：高/低段的确切切换阈值（未做 8/16/32/64/128 KiB 阶梯）、高段是否等价物理地址。

## 3. 命令流里的地址编码：`iova >> 4`

- 每个需要重定位的地址在命令缓冲里存成 **`iova >> 4` 的 32 位字**；
- 重定位 = 在命令流里搜索"抓取时的旧值 `old>>4`"，替换成"本次的 `new>>4`"；
- 旧值必须来自**同一次抓取**（`iova.txt` 与命令流配对），否则一处也匹配不到。

实测的地址字位置（`asset_report.py` 输出）：

| 资产 | cmdbuf 大小 | 地址字偏移 |
|---|---|---|
| `fcdyn`（64×64 动态 FC） | 32/16/368 | `0x078`=权重B、`0x098`=输入A、`0x110`=输出C |
| `fc_dyn512`（512×512 动态 FC） | 32/16/368 | 同上（`0x078`/`0x098`/`0x110`），B 落在高段 |
| `fc_const`（常量权重 FC） | 32/16/400 | `0x05c`=常量、`0x0c0`=输入、`0x138`=输出 |
| `bmm_qk` / `bmm_qk16` | 32/16/368 | `0x078`=B(K)、`0x098`=A(Q)、`0x110`=输出 |
| `bmm_pv16` | 32/16/592 | `0x050`=A(P)、`0x178`=B(V)、`0x1f0`=输出 |
| `softmax16` | 32/16/**1184** | `0x050`=输入、`0x128`=**输出**、`0x448`=**LUT** |
| `relu` | 32/16/336 | `0x050`=输入、`0x0f4`=输出 |
| `logistic` / `tanh` | 32/16/368 | `0x054`=输入、`0x070`=输出 |

规律：**偏移不是固定的**，随算子和命令流长度变化；一律"按值搜索"，不要按偏移写死。

## 4. 每个算子需要几块数据缓冲（映射逻辑的算子侧）

| 算子 | 运行时缓冲 | 说明 |
|---|---|---|
| 逐元素二元（ADD/MUL/SUB/MAX/MIN） | A、B、C（各 4 KiB 装 64 B 数据） | 3 处地址 |
| 一元（RELU/LOGISTIC/TANH） | A、C | 2 处地址；B 槽位写 0（重定位时必须跳过，否则 0 会匹配满屏零字） |
| BMM（QKᵀ / PV） | A、B、C | 3 处地址；B 是第二个运行时张量 |
| SOFTMAX | A、**LUT**、C | **3 块**：LUT 是 96 字节常量表，必须随资产一起重放，否则 kernel 算出全 0 |
| FC（动态权重） | A（激活）、B（权重 4 KiB～256 KiB）、C | 大权重会落到高段 |
| FC（常量权重） | A、**常量区 8 KiB**、C | 常量区内容来自 `.dla` 的静态数据；我们的重放**目前数值不稳**（见 §6） |

## 5. 缓存同步（映射正确≠数据可见）

- CPU 写 → 设备读：对**每个**要写的缓冲做 `DMA_BUF_IOCTL_SYNC(START|WRITE)` 与 `(END|WRITE)`；
- 设备写 → CPU 读：对输出缓冲做 `(START|READ)` / `(END|READ)`，**并且要等**（我们等 200 ms）；
- **命令缓冲也必须同步**——早期漏了这一步，表现为"偶发读到陈旧命令流"（修好后复现率明显下降）。

## 6. 已知未解（写在文档里，不猜测）

1. **常量权重 FC（8 KiB 常量区）**：`rc=0`、三处地址命中、内容与厂商抓取逐字节一致，
   但连跑 11 次只有 3 次数值正确（`dev=+127 vs exp=-128` 的饱和特征）。已排除：命令流、
   缓冲内容、8 KiB 对齐、ALLOC 的 type/align、命令缓冲 flush。**UNKNOWN：常量区是否要求只读映射/loader 写入顺序。**
2. 高段地址的**切换阈值**与语义（是否等价物理地址）未测。
3. `FREE`（op=1）驱动不支持；我们只 UNMAP。资源回收依赖进程退出，未验证长跑稳定性。

## 7. 复现方法

```bash
# 1) 抓一次（厂商 runtime 只用来"录一份合法提交"）
./probe/mkasset.sh  <op> <device.dla> <a.bin> <b.bin>      # 二元
./probe/mkasset_u.sh <op> <device.dla> <a.bin>             # 一元
# 2) 看映射
/usr/bin/python3 probe/mem_map_flow.py  probe/assets/<op>/cap.log
# 3) 看资产里有哪些缓冲、地址字在哪
/usr/bin/python3 probe/asset_report.py  probe/assets
# 4) 用我们自己的提交器跑（不碰 libneuron/neuronrt）
LD_LIBRARY_PATH=/data/local/tmp/npuops/lib ./probe/<demo> ...
```
