# 整块当「单个算子」重放：卡在哪（实测定位）

日期：2026-11-14 · 目标 `ops/block_qwen25_1l_full_fp16/model.dla`（40 op，H=64，T=8，fp16）

## 0. 结论（先纠正我上一轮的猜测）

我一度怀疑「大图换了寻址编码」，**不是**。真正的原因是：

> **这块图一次提交里带 `num_subcmds = 2`，而我们的资产只抓了第 1 个子命令，重放时还把 `num_subcmds` 硬写成 1。**

也就是说：我们只提交了半张图，输出缓冲的地址字在**没抓到的第 2 个子命令**里。

## 1. 证据链

| 观察 | 值 |
|---|---|
| `mdw_cmd_in@0x48`（num_subcmds） | **2**（我们 `npu_run.c` 里写死 `put32(&cmd, 0x48, 1)`） |
| 抓到的子命令描述符 | 只有 1 个（`SUBSCMD num_cmdbufs=3`），映射到 32 / 16 / 6240 B 三个 cmdbuf |
| MAP 表里的小 cmdbuf 对 | **两组** 32 B + 16 B（fd 9,10 与 fd 11,12）→ 与「两个子命令各带一套」吻合 |
| 命令流（6240 B, 1560 字）里在 DLA 窗口内的地址字 | 只有 **2 个**，都是输入 x（`0x50`、`0x340`） |
| 输出缓冲（`map19_fd14_len1000`，iova `0x25aee000`）的地址字 | 三个 cmdbuf 里**一个都没有** |
| 静态常量区（`fd=8`, 69632 B, iova `0xcbaa0000`）的地址字 | 同样**没有** |

后两条不是「找不到」，而是**本来就在第 2 个子命令里** —— 那一套 cmdbuf 我们没 dump。

## 2. 对比：3 op 的融合图为什么能成

`ops/gated_8x696_fp16`（LOGISTIC + MUL + MUL）→ `num_subcmds = 1`，命令流里 4 个地址字全是我们能 patch 的
（A 出现两次、B、C），一次提交跑完，与厂商输出逐字节相同。见 [`reports/npu-lib-fusion.md`](npu-lib-fusion.md)。

**分界线不是算子数，是子命令数。**

## 3. 要做成「整块 = 单个算子」，缺四件事

1. **抓取侧**：`probe/iolog2.c` 现在只解 `subcmd[0]` —— 要枚举 `num_subcmds` 个描述符，各 dump 自己的 cmdbuf 集；
2. **资产侧**：`probe/mkasset.py` 的「正好 3 个 cmdbuf」硬断言改成「每子命令一组」，`iova.txt` 变成按子命令分组；
3. **提交侧**：`probe/npu_run.c` 组装 `num_subcmds = N` 的 subcmd 数组（每项各自的 cmdbuf 描述符），
   并把地址字重定位扫到**所有**子命令的 cmdbuf；
4. **plan 侧**：`plan.txt` 从「一份 cmdbuf 集」变成「N 份」，`npu_lib` 的 `Plan` 相应分组。

四件都是**机械工作**，没有未知机制。风险点在「静态常量区」那块 68 KB 缓冲（它在 MAP 表里是真实分配，
所以是普通数据缓冲，可以按 A/B/C 同样的办法分配 + 填内容 + 重定位 —— 但常量区在自建提交器上的
重放契约仍未定（[`docs/ISSUE-const-fc.md`](../docs/ISSUE-const-fc.md) 的 3/11），整块路径要顺带把它验掉。

## 4. 今天能做到的

- 单子命令的融合图：**能**（SwiGLU 三算子已验证，逐字节）；
- 多子命令的整块：**必须**先把上面四件做完。做完之后，整块就是「一个资产、一次提交」——
  这也是离「块 = 单个算子」最近的路。
